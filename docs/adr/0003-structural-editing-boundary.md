# Free textual editing inside a preserved message structure

Allow text replacements and new non-authoritative context notes, including growing summaries, TODOs, and tables. Reject role changes, new system messages, and fabricated structured tool activity. A deterministic JSON context document provides editable text slots and read-only structural descriptors; original message objects retain non-text content and metadata in memory.

Preserve tool call IDs, names, arguments, images, and opaque thinking/signature metadata. Tool-result text is editable, but deletion/reordering operates only on complete tool exchanges, including all parallel calls and results. Reject incomplete exchanges atomically instead of silently repairing or flattening them. These restrictions prioritize inspectable, structurally consistent Pi inputs over the paper's unrestricted editing surface; they are project decisions, not paper requirements.

Validate at the next context boundary before publishing a new mirror, append intervening conversation activity, and reject stale baselines. Amended for editing UX: a dedicated tool stages generation-scoped operations, with one pending proposal per boundary. Only after validation and publication succeed may a complete successful edit-only exchange become a compact non-authoritative acceptance receipt in effective context. Mixed, failed, or incomplete exchanges remain whole; never surgically remove or rewrite individual signed calls. Reject no-op proposals and consecutive edit-only proposals until new substantive conversation activity, preventing receipt/re-edit loops. Rejection of a candidate at the boundary clears draft/overlay (a rejected tool call changes nothing; see the conflict amendment) but preserves the loop lock and activity checkpoint; only substantive activity or explicit OFF/session/compaction reset unlocks it. A third attempt cannot reopen the cycle merely because the second was rejected. The activity checkpoint follows a raw branch-entry ID, not projected message counts, so Pi-native history omissions cannot hide genuinely new user activity. Receipts are overlay-only and never trigger automatic continuation. A generation identifies a working-context editing revision, not an inference counter: append-only calls retain it and existing source IDs so separate read/write calls are usable; accepted edits or resets invalidate older generations. Whole-document replacement deletes omitted source units that the writer could have seen (superseded below: see the revision amendment). Invalid candidates discard both draft and overlay and fall back to normal input with a visible reason, rather than retaining the previous overlay. This fail-open-to-Pi behavior can reintroduce much larger context and user intent previously omitted by the model; it does not guarantee successful inference or semantic fidelity.

Amended for conflict handling: a rejected dedicated call is not an invalid candidate and changes nothing. When a file edit is pending or a proposal is already staged for the boundary, the later `context_edit` call alone is rejected as a conflict; the pending edit keeps the document and is validated normally at the next boundary, and the staged proposal keeps its place. A rejected call likewise leaves a previously accepted overlay in place; the loop lock is enforced by rejecting the call, not by discarding the overlay. Validation and discarding happen only at the boundary. After a boundary rejection the extension immediately republishes a normal-input document under the path already advertised for that inference, so the model never reads a withdrawn path; only if that publication fails is the document absent until the next inference. The tool result states that a staged edit is not yet applied, and boundary rejections remain visible through the status reason.

Amended for stale whole-document writes: each publication within a generation carries a read-only, increasing `revision`, and the extension remembers the revision at which every source unit first appeared. A candidate carrying an older revision may delete only units that existed at that revision; omitted units that first appeared later were never visible to its author and are retained after the written units in their original order. A revision the extension never published is rejected. This replaces the earlier rule that any omitted unit is deleted: deletion must be a decision about something the model actually saw, so a read in one call and a write in a later call cannot silently drop intervening activity, while the generation still stays stable across append-only calls.
